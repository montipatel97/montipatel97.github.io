DATA SKEW

What is data skew?

Data skew happens when data is distributed very unevenly across partitions. Spark is parallel, but the entire stage often waits for the slowest tasks.

40 MB55 MB48 MB8 GB 🔥

Three tasks may finish quickly while one task processes a massive partition. That one straggler controls the stage runtime.

Interview focus

Skew is not simply “big data.” It is an uneven distribution of work.

TYPES OF SKEW

Key skew vs partition skew

Key skewOne or a few values occur extremely frequently.Example: country = UNKNOWN
Partition skewOne partition contains far more data than others.May be caused by hot keys, bad repartitioning or input layout.

Key skew is a common cause of partition skew during key-based operations such as joins and aggregations.

Interview focus

Always identify the root cause. Adding partitions does not automatically split one extremely hot key.

WHY IT HURTS

Why skew destroys parallelism

Suppose 199 tasks finish in 2 minutes and one skewed task takes 40 minutes.

199 tasks ✓ 2 min1 skewed task 🔥 40 min

Even with hundreds of executors, the stage effectively waits for the long-running straggler.

Interview focus

Cluster utilization can look poor during the long tail because most resources are already idle while a few skewed tasks continue.

DETECTION

How to detect skew

Use Spark UI and compare task metrics within the same stage. Look for:

  • A few tasks with much longer duration
  • Large differences in input/shuffle read size
  • Large spill or memory pressure on only some tasks
  • A long tail where most tasks complete but a few remain

You can also profile key frequencies directly when investigating a suspected key.

Interview focus

Do not diagnose skew only from average stage time. Compare the distribution of individual task sizes and durations.

PROFILE THE DATA

Find hot keys

For a suspected key, inspect frequency distribution. For example:

Interview focus

A key that dominates the dataset is a candidate for skew mitigation, but first confirm it is actually responsible for the slow stage.

df.groupBy("customer_id") \
  .count() \
  .orderBy("count", ascending=False) \
  .show(20, truncate=False)
COMMON MYTH

Why more partitions may not fix skew

If 80% of records have key = 'UNKNOWN', hash partitioning still sends that key to one target partition.

Key A → P1Key B → P2UNKNOWN (80%) → P3 🔥Key C → P4

Changing from 200 to 1000 partitions may create more partitions for normal keys while the hot key remains concentrated.

Interview focus

More partitions solve insufficient parallelism; they do not automatically solve a single-key distribution problem.

AQE FIRST

Let Spark handle supported skew automatically

For supported shuffle-based joins, Adaptive Query Execution can detect skewed partitions using runtime statistics and split skewed work into smaller pieces, replicating the other side when needed.

Huge skewed partition→ AQE splits →smaller balanced tasks

This should usually be checked before writing complex manual salting logic.

Interview focus

Modern Spark can automatically optimize supported skew joins. Understand AQE first, then use manual techniques when the workload still needs them.

AQE LOGIC

How Spark identifies a skewed partition

A partition is generally considered skewed only when it crosses both a relative threshold compared with the median partition size and an absolute size threshold.

This prevents a tiny dataset with a merely uneven partition from being treated the same as a genuinely large problematic partition.

Interview focus

For interviews, remember the concept: relative imbalance + absolute size threshold. Check your Spark version for exact configuration behavior.

SALTING

What is salting?

Salting deliberately splits a hot key into multiple derived keys.

Instead of:

UNKNOWN→ one partition 🔥

Create:

UNKNOWN_0UNKNOWN_1UNKNOWN_2UNKNOWN_3UNKNOWN_4

Now records associated with the hot logical key can be distributed across multiple partitions.

Interview focus

Salting changes the physical distribution while preserving the logical join relationship through matching salted keys.

RANDOM SALTING

Salt the large skewed side

For a skewed large dataset, assign a salt value across a chosen range for hot-key records. Normal keys often do not need special handling.

Interview focus

Random salting distributes the heavy side, but the other join side must be prepared so matching salted keys still meet.

from pyspark.sql import functions as F

N = 10

salted_fact = fact_df.withColumn(
    "salt",
    F.when(F.col("customer_id") == "UNKNOWN",
           (F.rand() * N).cast("int"))
     .otherwise(F.lit(0))
)
SALTING THE OTHER SIDE

Replicate only what must match

For a skewed join, the smaller matching side can be replicated across the same salt values for the hot key. This is the cost of manual salting: more rows are created on one side to distribute the work on the other.

Interview focus

Never blindly explode the entire dimension table. Target the problematic key(s) where possible.

from pyspark.sql import functions as F

N = 10
salts = F.sequence(F.lit(0), F.lit(N - 1))

salted_dim = (
    dim_df
    .withColumn(
        "salt",
        F.when(F.col("customer_id") == "UNKNOWN", salts)
         .otherwise(F.array(F.lit(0)))
    )
    .withColumn("salt", F.explode("salt"))
)

result = salted_fact.join(
    salted_dim,
    ["customer_id", "salt"]
)
DETERMINISTIC SALTING

When deterministic salt is useful

Instead of random assignment, a stable secondary column can determine the salt. For example, a hash of another identifier can spread records reproducibly.

This can make debugging and repeatability easier when the data has a suitable secondary attribute.

Interview focus

The salt does not have to be random. The goal is a sufficiently balanced deterministic distribution while preserving correctness.

salted = fact_df.withColumn(
    "salt",
    F.pmod(F.hash("order_id"), F.lit(10))
)
AGGREGATION SKEW

Skew is not only about joins

A hot key can also create a huge aggregation partition. Sometimes a two-stage aggregation or a salted partial aggregation can distribute work:

salted partial aggregate→small intermediate results→final aggregate by original key

The exact approach depends on whether the aggregation operation can be safely decomposed and recombined.

Interview focus

Think carefully about aggregation semantics before salting. Count and sum are straightforward to combine; not every operation behaves the same way.

BROADCAST VS SALTING

Can broadcast avoid the problem?

If the non-skewed side is genuinely small enough, broadcasting it may avoid the shuffle-based join that exposes the skew in the same way. This can be simpler than salting.

But broadcasting a large dataset just to avoid skew can create a worse memory problem.

Interview focus

Before salting, ask: can a safe broadcast strategy remove the expensive redistribution?

WHEN NOT TO SALT

Salting has a cost

More complexity
Extra columns/logic
Replication on matching side
Potentially more data
Harder correctness testing
May be unnecessary with AQE

Use it for a measured skew problem—not as a default optimization pattern.

Interview focus

Manual salting is a targeted tool, not a general-purpose Spark performance setting.

PRODUCTION EXAMPLE

A realistic decision tree

  1. A join stage has a 35-minute long tail.
  2. Spark UI shows two partitions are dramatically larger.
  3. Key profiling reveals one customer category dominates.
  4. Check whether the small side can be broadcast safely.
  5. If not, verify AQE skew handling and supported join strategy.
  6. If skew remains, salt only the identified hot key(s).
  7. Replicate only required matching records on the smaller side.
  8. Measure shuffle bytes, task balance and end-to-end runtime.

Interview focus

This decision tree is stronger than answering every skew problem with “use salting.”

INTERVIEW READY

Skew & salting quick answers

What is skew?
Uneven distribution causing some tasks to process much more work.
How detect it?
Spark UI task duration and data-size imbalance.
Does repartition fix it?
Not necessarily for a single hot key.
What is salting?
Split a hot logical key into multiple derived keys.
Cost of salting?

Interview focus

🔥 Data Skew & Salting — Interview Vault

1. What is data skew in Spark?

Uneven data distribution where some partitions/tasks receive disproportionately more work.

2. Why is skew bad?

Parallel execution waits for straggler tasks, causing a long stage tail and poor resource utilization.

3. How do you identify skew?

Compare task durations and input/shuffle sizes in Spark UI and investigate key-frequency distribution.

4. Why doesn't increasing partitions always fix skew?

A single hot key can still hash to one target partition.

5. What is salting?

Adding a derived value to split one hot logical key across multiple physical keys.

6. Why do we replicate the smaller side when salting a join?

Each salted version of the hot key on the large side must find a corresponding matching key.

7. Should you salt every key?

No. Usually target measured hot keys; salting everything adds unnecessary data and complexity.

8. Random or deterministic salt?

Either can work. Deterministic salting can use a stable secondary identifier and is easier to reproduce.

9. Can AQE solve skew?

For supported shuffle-based joins, AQE can detect and split skewed partitions using runtime statistics.

10. Can broadcasting help with skew?

If the other side is safely small, broadcast can avoid the expensive shuffle-based join strategy.

11. When is salting a bad idea?

When there is no measured skew, AQE already solves it, or replication cost outweighs the benefit.

12. Can skew affect aggregations?

Yes. Hot grouping keys can create oversized aggregation partitions too.

🎯 Skew decision formula

Detect → Profile keys → Check broadcast → Check AQE → Salt only measured hot keys → Measure again.
