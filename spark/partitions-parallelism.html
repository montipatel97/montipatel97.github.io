PARTITIONS

What is a partition?

A partition is a logical chunk of a distributed dataset. Spark can assign work on different partitions to different tasks, enabling parallel processing.

For a stage, the partition layout is one of the main things that determines how much work can be split into tasks.

Interview focus

Think of partitions as units of distributed data; tasks are units of execution that process those partitions.

PARALLELISM

Why partitions matter

Too few partitions can underuse cluster resources because there are not enough independent tasks. Too many tiny partitions can create excessive scheduling and coordination overhead.

The goal is not to maximize the number of partitions—it is to balance parallelism against task overhead and partition size.

Interview focus

More partitions does not automatically mean faster. Always relate partition count to data volume and available compute.

INPUT PARTITIONS

Where do input partitions come from?

For file-based sources, Spark can split input files into partitions based on file format, file sizes and read configuration. The current Spark SQL tuning guide documents spark.sql.files.maxPartitionBytes as a file-read partition sizing control, with a default of 128 MB.

This is different from shuffle partitions: input partitioning and post-shuffle partitioning are separate concepts.

Interview focus

Never confuse file scan partitions with spark.sql.shuffle.partitions.

SHUFFLE PARTITIONS

spark.sql.shuffle.partitions

This setting controls the number of partitions used for many shuffled DataFrame/SQL operations such as joins and aggregations. Current Spark documentation lists the default as 200.

After a shuffle, the downstream stage can therefore have a partition count based on the shuffle configuration or adaptive execution decisions.

Interview focus

A common interview answer: input partitions come from reading data; shuffle partitions are used when Spark redistributes data for operations such as joins/aggregations.

spark.conf.get("spark.sql.shuffle.partitions")

spark.conf.set("spark.sql.shuffle.partitions", 400)
REPARTITION

repartition(): redistribute and rebalance

repartition(n) redistributes the data to create the requested partition count. This redistribution involves a shuffle, so it can be expensive, but it can increase or decrease partition count and help rebalance data.

You can also partition using columns, which is useful when you deliberately want a distribution aligned with later processing.

Interview focus

The key phrase: repartition performs a shuffle to redistribute data.

df = df.repartition(200)

# Repartition using a column
df = df.repartition(200, "country")
COALESCE

coalesce(): reduce partitions efficiently

coalesce(n) is commonly used to reduce the number of partitions while avoiding a full shuffle. This can be useful after a filter dramatically reduces data or when reducing output file count.

Because avoiding redistribution can preserve uneven partition sizes, coalesce is not simply a free replacement for repartition when you need balanced data.

Interview focus

Simple rule: reducing partitions without needing a full rebalance → consider coalesce; balanced redistribution or increasing partitions → repartition is generally the clearer choice.

# Reduce many partitions after filtering
small_df = filtered_df.coalesce(20)

Interview focus

Do not memorize only “repartition = shuffle, coalesce = no shuffle.” The nuance is that coalesce is mainly used to reduce partitions and can avoid a full redistribution.

PARTITIONING STRATEGY

Hash and range partitioning

When redistributing by a column, Spark can organize records according to partitioning expressions. Conceptually, hash partitioning distributes keys based on a hash; range partitioning groups records into ordered ranges.

Use the data and downstream workload to decide. A partitioning strategy can improve some later operations but may be useless—or harmful—if it adds an unnecessary shuffle.

Interview focus

Ask: what downstream operation benefits from this distribution? Partitioning is a workload decision, not decoration.

# Range-oriented distribution
df = df.repartitionByRange(100, "event_date")

Partitions vs executor cores

Suppose a stage has 400 tasks because it has 400 partitions, but your application can run only 40 tasks concurrently. Spark runs tasks in waves.

Increasing partitions can create more potential parallelism, but it does not create more CPU cores.

Interview focus

Partition count controls task granularity; executor resources control concurrency.

SMALL FILES

The small files problem

A large number of tiny files can create excessive metadata work, file-open overhead and many small tasks. Spark's file partitioning settings include an estimated file-open cost specifically to help account for this when grouping files into read partitions.

In data lakes, output partitioning should therefore consider downstream file sizes and not blindly produce thousands of tiny output files.

Interview focus

Many output partitions can mean many output files. Always think about both Spark task efficiency and storage-layer file efficiency.

STORAGE PARTITIONING

Partition pruning

Storage partitioning and Spark execution partitions are related but different ideas. If data is stored in directory partitions such as country=IN or date=2026-09-08, filters on those partition columns can allow Spark to avoid scanning irrelevant partitions.

This is called partition pruning and can reduce data read before the rest of the computation even begins.

Interview focus

Partition pruning is about skipping unnecessary stored data; it is not the same as calling repartition().

DATA SKEW

Uneven partitions are dangerous

Equal partition count does not guarantee equal partition size. If one key such as UNKNOWN contains a huge fraction of records, one shuffle partition can become much larger than the others.

HOT

The result is often that most tasks finish quickly while one or a few tasks remain running for much longer. We will cover salting and AQE skew handling later.

Interview focus

Skew is about unequal data distribution, not simply an incorrect number of partitions.

TUNING

How do you choose partition counts?

There is no universal magic number. Start from data size, cluster resources, task duration and observed skew. Inspect Spark UI metrics and tune based on actual workload behavior.

  • Too few partitions → large tasks, poor parallelism.
  • Too many partitions → tiny tasks and scheduling overhead.
  • Uneven partitions → stragglers and skew.
  • Repeated shuffles → consider whether repartitioning is actually helping.

Modern Spark can also use Adaptive Query Execution to coalesce post-shuffle partitions based on runtime statistics.

Interview focus

A strong production answer emphasizes measurement, Spark UI and workload-specific tuning—not a universal partition number.

PRODUCTION EXAMPLE

A realistic flow

Imagine a 500 GB fact dataset. You filter it down to 20 GB, then join and aggregate.

  1. The file scan creates input partitions based on the source/files.
  2. The filter may reduce data substantially without changing the conceptual need for existing upstream partition work.
  3. A join or aggregation can trigger a shuffle with downstream shuffle partitions.
  4. A deliberate repartition may be justified if downstream writes or processing need a specific distribution.
  5. A coalesce may be useful before writing when data has become much smaller and you want fewer output files.

Interview focus

Explain the reason for every repartition. Unnecessary repartitioning adds shuffle cost.

INTERVIEW READY

Rapid-fire partition questions

Q: What determines number of tasks?
A: The partitions processed by that stage are a primary driver.
Q: Does repartition shuffle?
A: Yes, it redistributes data.
Q: When coalesce?
A: Commonly when reducing partitions without needing a full rebalance.
Q: Default SQL shuffle partitions?
A: Current Spark docs list 200.
Q: What is skew?
A: Highly uneven data distribution causing some tasks to process much more data.
Q: Partition pruning?
A: Skipping irrelevant stored partitions during reads.

Interview focus

For any partition question, identify whether the interviewer means input files, Spark execution partitions, shuffle partitions, or storage partitions.

🔥 Partitions & Parallelism — Interview Vault

1. What is a Spark partition?

A logical chunk of distributed data that can be processed as a unit of work by a task.

2. What is the relationship between partition and task?

For a stage, tasks process the partitions assigned to that stage.

3. What is the difference between input and shuffle partitions?

Input partitions come from reading data; shuffle partitions are created for redistributed operations such as joins and aggregations.

4. repartition vs coalesce?

Repartition redistributes data through a shuffle. Coalesce is commonly used to reduce partitions while avoiding a full redistribution.

5. Does more partitions mean more executors?

No. It creates more task units; executors and cores determine how many can run concurrently.

6. What is spark.sql.shuffle.partitions?

A configuration controlling the number of partitions used for many shuffled SQL/DataFrame operations; current Spark documentation lists a default of 200.

7. What happens with too few partitions?

Tasks become larger and cluster parallelism may be underutilized.

8. What happens with too many partitions?

Tasks can become too small, increasing scheduling and coordination overhead.

9. What is partition skew?

Uneven data distribution where some partitions contain far more data and become slow straggler tasks.

10. What is partition pruning?

Skipping irrelevant storage partitions based on filters, reducing unnecessary reads.
