STREAMING 101

What is Structured Streaming?

Structured Streaming lets you express streaming computations using familiar Spark DataFrame/Dataset-style transformations. Spark treats the incoming stream as an unbounded table and incrementally updates the result as new records arrive.

Source→Streaming DataFrame→Transform→State/Result→Sink

Interview focus

The key interview sentence: write streaming logic declaratively; Spark incrementally executes it as data arrives.

BATCH VS STREAM

Batch vs streaming

BatchBounded input with a known end.Process yesterday's files.
StreamingUnbounded input that keeps arriving.Process events continuously.

The transformation logic can look similar. The major difference is that streaming must manage progress, state and recovery over an ongoing input.

Interview focus

Streaming is not simply a very fast batch job. It introduces unbounded input and long-lived state.

EVOLUTION

DStreams vs Structured Streaming

DStreams are the older Spark Streaming abstraction based on a sequence of RDD batches. Structured Streaming is the modern high-level API built on Spark SQL's optimized engine and structured DataFrame/Dataset model.

For modern data engineering interviews, Structured Streaming should be the primary focus, while DStreams are useful historical context.

Interview focus

Say: DStreams expose a sequence of RDD micro-batches; Structured Streaming uses the structured APIs and Spark SQL engine.

MICRO-BATCH

How micro-batch execution works

  1. New data becomes available.
  2. Spark determines the next offset/range to process.
  3. That range becomes a small batch.
  4. The Spark query plan processes the batch.
  5. State/progress is committed for recovery.
  6. The next trigger processes new data.

Micro-batch is the standard execution model and provides the familiar Spark execution engine for each small increment.

Interview focus

Think of it as a repeated sequence of small Spark jobs, coordinated with streaming progress and state.

CONTINUOUS

Continuous processing concept

Spark also has a low-latency continuous processing mode with different guarantees and operation support. It trades the standard micro-batch exactly-once model for lower latency and at-least-once semantics.

For most interview and production discussions, understand the trade-off rather than assuming continuous processing is universally better.

Interview focus

Micro-batch: general model and strong guarantees. Continuous mode: lower latency but different guarantees and limitations.

SOURCES

Where streaming data comes from

Kafka
Files
Sockets (demo)
Rate source (testing)
Other supported connectors

A source continuously exposes new records. Spark tracks progress so it knows what has already been processed.

Interview focus

Kafka is the most common interview source. Know that offsets represent progress through a partitioned event log.

KAFKA + SPARK

Typical ingestion architecture

Apps / Services→Kafka Topic→Spark Structured Streaming→Transform / Aggregate→Lake / DB / Sink

Spark reads records incrementally from Kafka partitions and tracks query progress through checkpointing.

Interview focus

Kafka stores the event log; Spark is the processing engine. Do not confuse Kafka offsets with Spark checkpoint state—they work together but are not the same thing.

READSTREAM

Creating a streaming DataFrame

Use readStream instead of read. The resulting DataFrame represents continuously arriving data.

Interview focus

The transformation APIs are intentionally familiar. The important difference is that the source DataFrame is streaming.

events = (
    spark.readStream
         .format("kafka")
         .option("kafka.bootstrap.servers", "host:9092")
         .option("subscribe", "events")
         .load()
)

events.printSchema()
SINKS

Where results go

After transformation, writeStream defines how results are emitted. Common choices include console for debugging, memory for testing, Kafka, files, and connector-specific sinks.

The sink must be compatible with the query's output mode and fault-tolerance requirements.

Interview focus

Always ask: what does the sink support, and is it idempotent or otherwise compatible with recovery semantics?

PROGRAMMING MODEL

The Result Table mental model

Imagine the streaming query continuously updates a conceptual Result Table.

Input keeps growing→Query updates result→Output mode decides what leaves

This mental model makes output modes easy to understand.

Interview focus

Output modes are about how changes in the result are emitted, not simply where the output is written.

OUTPUT MODES

Append, Update and Complete

AppendEmit rows newly added to the final result.
UpdateEmit rows changed since the previous trigger.
CompleteEmit the entire result table every trigger.

Supported modes depend on the query. Aggregations and event-time windows have specific compatibility constraints.

Interview focus

Do not memorize modes in isolation—connect them to whether an old result can still change.

TIME

Processing time vs event time

Event timeWhen the event actually occurred.
Processing timeWhen Spark processed the event.

Network delays, retries and offline devices mean these can differ significantly.

Interview focus

For accurate business windows, event time is often more meaningful than processing time.

LATE DATA

Why late events are difficult

Suppose a 10:00 event arrives at 10:12. If the 10:00 window was already considered complete, Spark must decide whether to update old state or discard data.

10:00 event happened10:05 window end10:12 arrives late 🔥

Interview focus

Late data requires a policy. Without bounded state, a streaming query could keep every historical window forever.

WATERMARKING

What a watermark means

A watermark defines how long the engine should continue expecting late data relative to observed event-time progress. It provides a threshold used for handling sufficiently late data and for state cleanup in supported stateful operations.

It is not a guarantee that data arrives on time, and it does not mean every event inside the delay is guaranteed to be processed.

Interview focus

Watermark = a practical boundary for lateness and state retention, not a perfect clock.

WINDOWS

Event-time window aggregation

Common windows include tumbling windows, sliding windows and session-style windows. Windowing converts an unbounded stream into meaningful time groups.

Interview focus

Window size and slide duration answer different questions: how wide is each bucket, and how frequently do buckets begin?

from pyspark.sql import functions as F

windowed = (
    events
      .withWatermark("event_time", "10 minutes")
      .groupBy(
          F.window("event_time", "5 minutes"),
          "event_type"
      )
      .count()
)
STATEFUL STREAMING

What is state?

Stateless operations can process each record independently. Stateful operations must remember something from previous batches: counts, windows, deduplication keys or join matches.

Batch 1→State→Batch 2→Updated State

Interview focus

State is the main reason streaming systems need careful checkpointing, watermarks and operational monitoring.

CHECKPOINTING

How failure recovery works

A checkpoint location stores progress information and state required to recover a streaming query. After a failure, Spark can restart and continue using recorded progress rather than treating the entire stream as brand new.

Use durable, fault-tolerant storage for production checkpoints.

Interview focus

Checkpointing is central to recovery. Do not place production checkpoints in ephemeral local storage.

query = (
    result.writeStream
          .format("parquet")
          .option("checkpointLocation", "/durable/checkpoints/orders")
          .outputMode("append")
          .start("/data/output/orders")
)
GUARANTEES

Exactly-once vs at-least-once

Structured Streaming's standard fault-tolerance story relies on replayable sources, tracked progress/checkpoints and sinks that can handle reprocessing appropriately. End-to-end semantics depend on the complete source-to-sink design.

Do not claim that “Spark always makes every external system exactly once.” The sink and its idempotency/transaction behavior matter.

Interview focus

Exactly-once is an end-to-end property. Always discuss source progress + checkpointing + sink behavior.

TRIGGERS

When does Spark process data?

Default processingProcess available data repeatedly.
Fixed intervalRequest a processing interval.
Available-now styleProcess currently available backlog and stop.

Trigger choice balances latency, scheduling overhead and how you want to handle available data.

Interview focus

A smaller trigger interval does not magically make every query faster; processing time must still be considered.

STREAMING JOINS

Stream-static vs stream-stream

Stream-staticContinuously enrich incoming events with reference data.
Stream-streamMatch records arriving on two unbounded streams; often requires time constraints and state management.

Stream-stream joins are more complex because both sides can continue producing matches indefinitely without bounded state conditions.

Interview focus

When both sides are unbounded, ask: how will old unmatched state eventually be removed?

DEDUPLICATION

Handling duplicate events

Streaming systems can receive retries or duplicate events. Deduplication typically requires remembering identifiers for some retention period, which means it is a stateful operation.

Watermark-aware approaches can bound how long old deduplication state is retained.

Interview focus

Deduplication is not free: exact duplicate detection over infinite history would require unbounded state.

FOREACHBATCH

Why foreachBatch is useful

foreachBatch gives access to each micro-batch as a regular DataFrame. This is useful when integrating with sinks or batch-style logic that is easier to implement per micro-batch.

You still need to design idempotency and recovery carefully because a batch can be retried.

Interview focus

foreachBatch is powerful, but it does not automatically make an external side effect exactly once.

OPERATIONS

Monitoring a streaming query

Input rate
Processing rate
Batch duration
Input backlog
State size
Watermark progress

A critical production symptom is when incoming data arrives faster than the query can process it. Backlog and latency then grow.

Interview focus

Streaming performance is about sustained throughput, not just how fast one batch finishes.

PRODUCTION CASE

End-to-end clickstream pipeline

  1. Events arrive continuously in Kafka.
  2. Spark reads the stream and parses the payload.
  3. Invalid records are filtered or routed separately.
  4. Events are enriched with static reference data.
  5. Event-time watermark bounds late data/state.
  6. Window aggregation calculates metrics.
  7. Results are written with a durable checkpoint.
  8. Input rate, batch duration and state size are monitored.

Interview focus

This is a strong interview architecture because it naturally introduces Kafka, parsing, state, watermarking, checkpoints and sinks.

🔥 Structured Streaming — Interview Vault

1. What is Structured Streaming?

A scalable streaming engine where computations are expressed using structured Spark APIs and incrementally executed as new data arrives.

2. What is the default execution model?

Micro-batch processing: incoming data is processed as a sequence of small batch jobs.

3. DStreams vs Structured Streaming?

DStreams are based on sequences of RDD batches; Structured Streaming uses DataFrames/Datasets and the Spark SQL engine.

4. Event time vs processing time?

Event time is when the event happened; processing time is when Spark processed it.

5. What is a watermark?

A lateness threshold used to help handle late data and bound state in supported stateful operations.

6. What are output modes?

Append emits newly finalized rows, Update emits changed rows, and Complete emits the full result table.

7. Why is checkpointing needed?

To record progress and state so a failed query can recover and continue safely.

8. What is stateful processing?

The query retains information across batches, such as aggregates, windows, deduplication or join state.

9. Why are stream-stream joins harder?

Both inputs are unbounded, so state must be bounded and old unmatched records eventually cleaned up.

10. Is exactly-once automatic for every sink?

No. End-to-end semantics depend on replayable sources, progress tracking and appropriate sink behavior.

11. Why use foreachBatch?

It lets you handle each micro-batch as a regular DataFrame for integration with batch-oriented logic or sinks.

12. What do you monitor?

Input rate, processing rate, batch duration, backlog, state size and watermark progress.

🎯 Streaming mental model

New data → Track progress → Process increment → Update state → Emit result → Checkpoint → Recover safely.
