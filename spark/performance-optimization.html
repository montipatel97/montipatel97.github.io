PERFORMANCE MINDSET

How to think about Spark performance

Most slow Spark jobs are not fixed by randomly increasing memory. Start by asking four questions:

How much data is read?
How much data moves?
How balanced is the work?
How efficiently is CPU/memory used?

This module turns those questions into a repeatable optimization workflow.

Interview focus

The best Spark engineer does not memorize configuration values—they identify the actual bottleneck first.

BIG PICTURE

The Spark optimization pipeline

Your Code→Logical Plan→Optimized Plan→Physical Plan→Runtime / AQE

For DataFrame and SQL workloads, Spark can analyze and optimize plans before execution, then adaptive execution can use runtime statistics to further optimize parts of the plan.

Interview focus

Always separate compile/planning-time optimization from runtime adaptation.

CATALYST

Catalyst Optimizer

Catalyst is Spark SQL's optimizer framework. With DataFrames and SQL, Spark can reason about the computation as a plan instead of immediately executing every line.

That gives Spark opportunities to rewrite expressions, push filters closer to data sources, prune unused columns and choose physical strategies.

Unresolved / logical intent
↓
Analyzed plan
↓
Optimized logical plan
↓
Physical plan

Interview focus

A key reason DataFrame/SQL APIs are often preferred over manually controlling low-level execution is that Spark has more optimization information available.

PUSHDOWN

Predicate pushdown

If a filter can be executed by the data source, Spark may push that predicate down so fewer rows are read into the Spark execution pipeline.

Conceptually:

Bad flowRead 1 TB → filter → keep 20 GB
Better flowSource filters → read closer to 20 GB

Actual pushdown support depends on the source, file format and expression.

Interview focus

Filter as early as possible, but remember that whether a predicate is truly pushed into the source depends on the source capabilities.

COLUMN PRUNING

Read fewer columns

Columnar sources can often avoid reading columns that are not needed. If your query selects only three columns from a very wide table, Spark's optimized plan may scan only those required columns.

Avoid carrying unnecessary payload through joins, shuffles and aggregations.

Interview focus

A simple optimization with large impact: select only required columns before expensive operations.

PARTITION PRUNING

Skip unnecessary storage partitions

If data is stored using partitioned layouts such as date=..., filtering on those partition columns can allow Spark to skip entire storage partitions.

This reduces data scanned before execution work even begins.

Interview focus

Partition pruning skips irrelevant stored data. Do not confuse it with repartitioning data during a Spark job.

TUNGSTEN

What people mean by Tungsten

Tungsten is commonly used to describe Spark's engine-level execution optimizations around efficient memory management and CPU-efficient execution.

At interview level, focus less on treating Tungsten as one magic feature and more on the practical idea: Spark tries to reduce overhead and execute structured operations efficiently.

Interview focus

Avoid vague claims like “Tungsten just makes Spark faster.” Explain the underlying goal: efficient memory and CPU use.

WHOLE-STAGE CODEGEN

Reduce execution overhead

Instead of treating every physical operator as an isolated heavyweight step, Spark can generate efficient code that combines compatible operations into larger execution pipelines.

Filter+Project+Expression→Generated execution pipeline

This reduces some function-call, object and intermediate processing overhead for supported workloads.

Interview focus

Whole-stage code generation is about efficiently executing compatible operator pipelines, not making every Spark operation automatically free.

CACHE & PERSIST

Cache only when reuse justifies it

Caching can be powerful when the same expensive dataset is reused across multiple downstream actions or branches. It can also waste memory and increase pressure if cached data is used only once.

Cache/persist is lazy: storage is generally materialized when an action causes the dataset to be computed.

Interview focus

The first question is not “Can I cache this?” It is “Will this expensive dataset be reused enough to justify the memory/storage cost?”

df = expensive_transformation(raw_df)

# Reused multiple times
df.cache()

df.groupBy("country").count().show()
df.groupBy("device").count().show()

df.unpersist()
SERIALIZATION

Serialization and object overhead

Distributed execution requires data and tasks to cross process or machine boundaries. Serialization cost can therefore matter, especially with object-heavy workloads.

For structured workloads, DataFrames and Spark SQL can often avoid some of the Python-object overhead associated with row-by-row Python processing.

Interview focus

Performance problems involving Python UDFs are often about crossing execution boundaries and losing optimizer visibility—not merely “Python is slow.”

UDFS

Avoid unnecessary Python UDFs

Prefer built-in Spark SQL/DataFrame functions when they express the same logic. Built-in expressions are visible to Spark's optimizer and can participate in optimized execution paths.

Preferred when possibleBuilt-in Spark expressions
Use when neededPython UDF for logic unavailable natively

Interview focus

Never say “never use UDFs.” Say: prefer native expressions when possible because they integrate better with optimization and execution.

PARTITIONS

Right-size parallelism

Too few partitions can leave resources underutilized. Too many can create excessive scheduling overhead and tiny tasks.

For SQL workloads, Spark exposes controls around file partitioning and shuffle partitioning; AQE can also coalesce post-shuffle partitions using runtime statistics.

Interview focus

Partition tuning should be based on data size, task metrics, cluster capacity and skew—not a magic number.

JOINS

Optimize the largest movement first

Joins are often expensive because they can move large datasets. Before tuning executor memory, inspect whether you can:

  • Filter before the join
  • Select fewer columns
  • Broadcast a genuinely small side
  • Pre-aggregate when semantics allow
  • Address skewed keys

Interview focus

Reducing shuffled bytes is often more valuable than micro-optimizing code inside a task.

AQE

Let runtime statistics adapt execution

Adaptive Query Execution uses runtime statistics to re-optimize parts of the query plan. Current Spark documentation describes AQE features including post-shuffle partition coalescing, adaptive join conversion and skew handling.

Coalesce
avoid too many tiny post-shuffle tasks
Join adaptation
use runtime sizes
Skew handling
split problematic partitions

Interview focus

AQE is powerful, but you should still understand the underlying shuffle, partition and join problems it is adapting to.

SMALL FILES

Small files are a system problem

Thousands of tiny files can increase metadata work, file-open overhead and create excessive small tasks. A job may therefore be bottlenecked before meaningful computation begins.

Optimize output file counts with downstream readers in mind; do not blindly coalesce everything to one file.

Interview focus

File layout affects both storage and compute performance. The best number of files depends on data volume and downstream workload.

EXPLAIN

Read the plan before tuning

Use explain("formatted") to inspect what Spark intends to execute. Look for:

  • Unexpected exchanges/shuffles
  • Join strategy
  • Filters and projections occurring too late
  • Python UDF boundaries
  • Large scans

Interview focus

If you have not inspected the plan, you are guessing.

df.explain("formatted")

Interview focus

The strongest debugging loop is explain → run → Spark UI → identify bottleneck → make one change → measure again.

CASE STUDY

Slow job → diagnosis → optimization

Scenario: A daily job reads 800 GB, joins a large fact table with several dimensions, then aggregates. It suddenly takes 90 minutes.

  1. Inspect explain: a large join triggers a major exchange.
  2. Spark UI: most tasks finish in 8 minutes, but a few run for 70 minutes.
  3. Diagnosis: skew on a hot key.
  4. Also notice filters happen after a join.
  5. Move selective filters before the join and reduce columns.
  6. Validate AQE/skew handling and reassess join strategy.
  7. Re-run and compare shuffle bytes and task distribution.

Interview focus

Optimization is a hypothesis-and-measure process. A faster job should have evidence: less data scanned, less shuffle, fewer stragglers or better resource utilization.

🔥 Spark Performance — Interview Vault

1. How do you optimize a slow Spark job?

Inspect the plan and Spark UI, identify whether the bottleneck is scan, shuffle, skew, partitioning, join strategy or resource pressure, then make and measure targeted changes.

2. What is Catalyst?

Spark SQL's optimizer framework that analyzes and optimizes structured query plans.

3. What is predicate pushdown?

Executing a supported filter closer to the data source so less data is read into Spark.

4. What is column pruning?

Reading only columns required by the query when the source and plan support it.

5. When should you cache?

When an expensive dataset is reused enough to justify its memory/storage cost.

6. Why prefer built-in functions over Python UDFs?

Built-in expressions are better integrated with Spark's optimizer and execution engine.

7. How does AQE help?

It uses runtime statistics to adapt execution, including post-shuffle partition coalescing and other adaptive optimizations.

8. What is the small files problem?

Too many tiny files increase metadata, file-open and task scheduling overhead.

9. How do you detect skew?

Inspect partition/task metrics for a few disproportionately large or slow tasks.

10. What is the most important optimization principle?

Read less, move less, and use measured evidence to identify the actual bottleneck.

🎯 Production optimization formula

Explain → Measure → Find bottleneck → Change one thing → Measure again.

Never celebrate an optimization until you can show what became better: scan volume, shuffle bytes, task balance, runtime or resource usage.
