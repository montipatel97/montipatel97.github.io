EXECUTION MODEL

Transformations build; actions trigger

This distinction is one of the most important ideas in Spark.

TransformationDefines a new dataset / plan
LazyNo immediate distributed execution
ActionTriggers computation or materializes output

Spark records transformations as lineage or a logical plan. Execution is triggered when Spark needs a result—for example through an action or a write.

Interview focus

The short interview answer: transformations are lazy and define new datasets; actions trigger execution.

LAZY EVALUATION

Why does Spark wait?

Suppose you filter, select columns and then aggregate. Spark does not need to materialize every intermediate result exactly as written in your code. By waiting until an action, it can analyze the complete computation and plan execution.

This is a major reason Spark can optimize pipelines and avoid unnecessary intermediate work.

Interview focus

Do not say lazy evaluation means “Spark does nothing.” It builds lineage/plans and prepares the computation; distributed execution is deferred.

df2 = df.filter("status = 'ACTIVE'")   # lazy
df3 = df2.select("id", "amount")        # lazy
df4 = df3.groupBy().sum("amount")       # lazy

df4.show()                              # triggers execution
TRANSFORMATIONS

Common transformations

Transformations return a new distributed dataset/DataFrame and remain lazy.

filter / whereKeep matching records
selectChoose/project columns
withColumnAdd or replace a column
joinCombine datasets
groupByDefine aggregation grouping
distinctRemove duplicates logically
orderByDefine ordering
repartitionRedistribute partitions

Some transformations are narrow and others involve wide dependencies or shuffle. We will go much deeper into that later.

Interview focus

Transformation does not mean “cheap.” A lazy transformation may eventually require a very expensive shuffle when execution is triggered.

ACTIONS

Common actions

Actions require Spark to execute the required lineage or plan and either return a result to the driver or materialize output.

count()Return row/record count
collect()Bring all results to driver
first() / take()Return a small result set
show()Display rows
write...Materialize output to storage

Important: collect() can be dangerous for large datasets because the result must fit in the driver's memory.

Interview focus

Mention driver memory whenever discussing collect(). This is a common production and interview trap.

API DETAILS

Same idea across RDD and DataFrame APIs

RDD examples use operations such as map and filter; DataFrame examples use select, filter, groupBy and others. The common concept is that transformations define distributed computation and actions trigger it.

Interview focus

Do not mix APIs accidentally. For example, map is an RDD-style transformation, while DataFrame work is generally expressed with structured column operations.

DEPENDENCIES

Narrow transformations

With a narrow dependency, an output partition depends on a limited, known subset of input partitions. This often allows Spark to pipeline operations without redistributing all data.

Typical conceptual examples include operations such as map and filter.

Interview focus

Narrow means a dependency pattern, not simply “fast.”

DEPENDENCIES

Wide transformations and shuffle

With a wide dependency, output partitions depend on data from multiple input partitions. Spark must redistribute data to satisfy the required partitioning relationship, creating a shuffle and commonly a stage boundary.

Grouping, aggregations, many joins and explicit repartitioning are common places where shuffle may appear.

Interview focus

The correct causal story is: wide dependency → redistribution/shuffle requirement → network/disk/coordination cost → likely stage boundary.

PIPELINING

A narrow pipeline vs a shuffle boundary

Imagine this chain:

Read
→ filter
select
→ map-like projection
same stage possible
→ groupBy
shuffle boundary
→ aggregate stage

The exact physical plan depends on the API and optimizer, but this mental model is excellent for understanding why some pipelines remain pipelined while others require redistribution.

Interview focus

This is the bridge to Jobs → Stages → Tasks. Stage boundaries are strongly tied to shuffle dependencies.

RECOMPUTATION

Actions can recompute lineage

If you run multiple actions on the same derived dataset, Spark may recompute the lineage for each action unless relevant results are persisted.

cache() or persist() marks a dataset for reuse after it is computed, trading storage resources for reduced recomputation.

Interview focus

Never cache everything. Persist when repeated reuse makes the saved computation worth the memory/storage cost.

MATERIALIZATION

Why write is a key execution point

Writing output requires Spark to actually produce the final data. A pipeline can therefore be completely lazy until a write operation materializes it.

Interview focus

Explain that lazy transformations build the plan, while an output action/write forces Spark to execute the required upstream computation.

INTERVIEW PATTERNS

Questions interviewers love

Q: Does filter() execute immediately?
A: No. It is lazy; execution happens when an action requires the result.
Q: Is groupBy() an action?
A: No. It is a transformation, though its eventual execution may require a shuffle.
Q: Why is collect() risky?
A: It moves the entire result to driver memory.
Q: Why is laziness useful?
A: Spark can analyze the computation before executing and avoid unnecessary intermediate materialization.

Interview focus

For every operation, train yourself to answer three things: lazy or action? narrow or wide? does it move data to the driver?

🔥 Transformations & Actions — Interview Q&A

1. Transformation vs action?

A transformation defines a new distributed computation lazily; an action triggers execution and returns/materializes a result.

2. Why is Spark lazy?

Deferring execution lets Spark analyze the required computation before running it and avoid unnecessary intermediate materialization.

3. Does every transformation create a stage?

No. Narrow transformations can often be pipelined. Shuffle dependencies commonly introduce stage boundaries.

4. Is groupBy an action?

No. It is a transformation. Its eventual execution can require a wide dependency and shuffle.

5. What happens with collect()?

The result is brought to the driver, so it is unsafe for large results that cannot fit in driver memory.

6. What is a narrow dependency?

An output partition depends on a limited known subset of parent partitions.

7. What is a wide dependency?

Output partitions require data from multiple input partitions, requiring redistribution and commonly a shuffle.

8. Why can repeated actions be expensive?

Without persistence, Spark may recompute the required lineage for each action.

9. Is cache an action?

Calling cache marks the dataset for persistence; data is actually populated when a subsequent computation evaluates it.

10. Give one execution story.

Transformations build lineage or a plan → action triggers a job → Spark divides work around dependencies → tasks process partitions on executors.
