EXECUTION MODEL

The one hierarchy you must never confuse

1ApplicationYour complete Spark program
2JobTriggered by an action
3StageTasks separated by dependencies/shuffles
4TaskUnit that processes a partition

The clean mental model is:

Application → Job → Stage → Task → Partition

A Spark application can contain multiple jobs. Each job is divided into stages. Each stage contains tasks. Tasks process partitions in parallel on executors.

Interview focus

If an interviewer asks the difference between job, stage and task, answer using this hierarchy before giving individual definitions.

APPLICATION

What is a Spark application?

A Spark application is your complete program running with its own driver and executor processes. It begins when you submit the application and contains the work triggered by actions during its lifetime.

One application can execute many jobs. This is important: a Python script is not automatically “one Spark job”. Every action can trigger separate work.

Interview focus

Application = the whole Spark program/session. Job = a computation triggered inside that application.

JOB

What creates a Spark job?

A job is created when Spark needs to evaluate an action. Examples commonly include count(), collect(), save(), and output operations that materialize a result.

Two actions on the same lineage can therefore produce two jobs and potentially recompute upstream work unless relevant data has been persisted.

df.filter(...)lazy.select(...)lazy.count()ACTION → JOB

Interview focus

Spark's own terminology describes a job as a parallel computation spawned in response to an action. Multiple jobs can exist inside one application.

DAG

What happens between the action and execution?

Spark examines the lineage/dependency graph required to produce the action's result. This graph is a Directed Acyclic Graph (DAG): directed because dependencies have an order, and acyclic because a computation cannot depend on itself in a loop.

The DAG describes what needs to be computed and how datasets depend on previous datasets. Spark then organizes the computation into executable stages.

Interview focus

A DAG is not itself a stage. The DAG describes the dependency graph; Spark breaks the required work into stages.

STAGE

What is a stage?

A stage is a set of tasks that can execute according to the dependency structure before downstream work requires data produced by another stage.

The most useful interview shortcut is: shuffle dependencies commonly create stage boundaries. Narrow transformations can often be pipelined together, while wide dependencies require redistribution and split execution into stages.

Stage 1Read → filter → selectnarrow / pipelined work
SHUFFLE
stage boundary
Stage 2aggregate → final resultconsumes redistributed data

Interview focus

Avoid saying “every wide transformation always creates exactly one extra stage” as a universal rule. The robust concept is that shuffle dependencies introduce boundaries in the execution plan.

TASK

What is a task?

A task is the smallest unit of work Spark sends to an executor. A stage is broken into many tasks so its partitions can be processed in parallel.

The core mental model is: one task processes one partition for that stage. If a stage has 200 partitions to process, it can have roughly 200 tasks for that stage.

Tasks do not necessarily all run at the same instant. Actual concurrency is limited by available executor cores/slots and cluster resources.

Interview focus

Do not confuse number of tasks with number of executors. Tasks are scheduled onto executor resources over time.

PARTITIONS

Why partitions determine task parallelism

Partitions are the units into which a distributed dataset is split. Spark uses those partitions to divide work among tasks.

Dataset
P1P2P3P4
↓
Task 1Task 2Task 3Task 4

More partitions can increase potential parallelism, but too many tiny partitions can create task scheduling overhead. Too few large partitions can leave cluster resources idle.

Interview focus

The number of partitions is a major driver of the number of tasks, but physical execution details can change as Spark plans and exchanges data.

WALKTHROUGH

Follow one DataFrame from code to tasks

Consider this example:

Interview focus

Walk through it in order: transformations → action → job → stages → tasks.

orders = spark.read.parquet("/orders")

result = (
    orders
      .filter("amount > 100")
      .groupBy("country")
      .sum("amount")
)

result.show()
STEP BY STEP

Exactly what happens in that example

  1. Read: Spark defines the input.
  2. filter: a lazy transformation; the computation is not executed immediately.
  3. groupBy: another lazy transformation, but the eventual aggregation requires records to be grouped by key.
  4. show: an action requiring Spark to execute the required computation.
  5. Job: Spark creates a job for the action.
  6. Stage 1: read/filter work runs on input partitions.
  7. Shuffle: data is redistributed so matching countries can be aggregated together.
  8. Stage 2: tasks consume shuffled partitions and complete aggregation.

The exact physical plan and stage count depend on Spark version, data source, configuration and optimizer decisions, but this is the correct conceptual execution story.

Interview focus

Interviewers care more about the causal chain than memorizing a fixed number of stages for every code snippet.

MULTIPLE JOBS

Why two actions can create two jobs

Consider:

filtered = df.filter("amount > 100")

filtered.count()     # Job 1
filtered.show()      # Job 2

The same logical lineage may be needed for both actions. Without persistence, Spark can recompute required upstream work. If the intermediate result is reused heavily and is expensive to rebuild, caching/persisting may help.

Interview focus

The key concept: action boundaries create jobs. Persistence affects whether repeated jobs can reuse computed partitions.

SHUFFLE

The most important stage boundary

During a shuffle, data is redistributed between partitions. This can involve network transfer, serialization, disk I/O, sorting and memory pressure. The upstream side produces shuffle data; downstream tasks read the required shuffled partitions.

That dependency means downstream stage tasks generally cannot complete until the required upstream shuffle output is available.

Interview focus

When debugging a slow Spark job, look at shuffle read/write metrics in the Spark UI and identify why the redistribution happened.

PARALLELISM

Tasks vs cores vs executors

Suppose a stage has 200 tasks. Suppose your application has enough executor capacity to run 20 tasks concurrently. Spark does not need 200 executors; it can run the tasks in waves.

Wave 120 concurrent tasks
Wave 220 concurrent tasks
...until all 200 finish

This distinction is crucial for tuning: partitions define potential task count, while executor resources define how much of that work can run concurrently.

Interview focus

Never equate partitions, tasks, executor count and cores. They are related but different layers.

FAULT TOLERANCE

What if a task fails?

Task execution is monitored and Spark can retry failed work according to its execution behavior and configuration. Because Spark knows lineage/dependencies, lost computation can often be recomputed.

A repeated task failure can eventually cause its stage—and therefore the job—to fail if Spark cannot successfully complete the required work.

Interview focus

Explain failure from bottom up: task retry → stage cannot complete if required tasks repeatedly fail → job cannot complete.

DEBUGGING

How this appears in Spark UI

The Spark UI exposes Jobs and Stages views. A job detail can show its DAG visualization and associated stages; stage details expose task progress and metrics such as input/output and shuffle read/write.

This is where your conceptual understanding becomes practical: if you see one stage with a few very slow tasks, think skew or uneven partition sizes; if you see heavy shuffle read/write, investigate the redistribution.

Interview focus

For production interviews, always connect Job → Stage → Task concepts to how you would inspect them in Spark UI.

🔥 Jobs, Stages & Tasks — Interview Vault

1. Explain Job → Stage → Task in 30 seconds.

An action triggers a Spark job. Spark analyzes the required dependency graph and divides the job into stages around execution dependencies, especially shuffle boundaries. Each stage is divided into tasks, which process partitions in parallel on executors.

2. Does every action create a job?

Actions are the operations that trigger the computation required to produce a result. In normal Spark execution, an action creates the corresponding job work for that computation.

3. What creates a new stage?

Stage boundaries are closely associated with shuffle/wide dependencies because downstream computation needs redistributed output from upstream work.

4. How is the number of tasks determined?

Tasks are tied to the partitions a stage processes. More partitions generally mean more tasks for that stage.

5. Is one task equal to one executor?

No. Tasks are scheduled onto executor resources. An executor can execute many tasks over time and may execute multiple concurrently depending on available cores.

6. If I have 1,000 tasks, do I need 1,000 cores?

No. Tasks can run in waves. Available executor cores determine concurrency; remaining tasks wait to be scheduled.

7. Can one Spark application have multiple jobs?

Yes. Multiple actions during the lifetime of an application can trigger multiple jobs.

8. Why can two actions repeat work?

Without persistence, each action may need to recompute required lineage. Cache/persist can allow reuse of computed partitions when appropriate.

9. What is the relationship between DAG and stage?

The DAG represents dependencies in the computation. Spark uses those dependencies to organize the work into executable stages.

10. What do you inspect in Spark UI for a slow stage?

Task duration distribution, locality, input/output, shuffle read/write, GC and other task metrics. A few unusually slow tasks can indicate skew.

11. What happens if one task repeatedly fails?

Spark retries task execution according to its behavior/configuration. If required work cannot complete, the stage and therefore the job can fail.

12. Give the complete execution story from PySpark code.

Transformations define lineage lazily → an action requests a result → Spark creates job work → dependencies split execution into stages → each stage creates tasks for partitions → tasks are scheduled onto executor resources → results are returned or written.

🎯 The one sentence to remember

Action → Job → dependency analysis → Stages → partition-based Tasks → Executors execute Tasks.

This is the foundation for everything next: partitions, shuffle, joins, caching, skew and optimization all make more sense once this hierarchy is clear.
