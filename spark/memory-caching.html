MEMORY MINDSET

Why memory matters in Spark

Spark is often described as an in-memory engine, but real workloads continuously balance memory, CPU, network and disk. Memory problems usually appear when a task needs too much working space, too much data is cached, or a few partitions are abnormally large.

Execution
shuffle, join, sort, aggregate
Storage
cache & persisted blocks
Objects
JVM/Python overhead
GC
cleanup overhead

Interview focus

Do not diagnose every OOM by simply adding executor memory. First identify what is consuming memory.

UNIFIED MEMORY

Execution vs storage memory

Spark's unified memory model has two major consumers:

Execution Memory
joins • sorts • aggregations • shuffles
Storage Memory
cached & persisted datasets

They share a unified region. Execution can evict storage when necessary, while storage does not symmetrically evict execution memory.

Interview focus

Execution memory is temporary working memory. Storage memory is for retained cached data.

MEMORY FRACTIONS

M and R mental model

At a high level, Spark defines a unified memory region often described as M. Within it, R is a storage subregion whose cached blocks are protected from eviction by execution.

JVM Heap
Reserved for user objects & metadata
M: Unified execution + storage
R: protected storage region

Defaults are designed for general workloads; changing fractions without understanding GC and workload behavior can make things worse.

Interview focus

For interviews: M is the shared execution/storage region; R is the protected storage portion inside it.

EXECUTION MEMORY

Where execution memory is used

Execution memory is needed for operations that require working sets while computing:

  • Shuffle sorting
  • Hash aggregations
  • Sort-merge joins
  • Hash-based joins
  • Large grouping operations

If the working set cannot remain in memory, Spark can spill intermediate data to disk. Spill is often slower, but it allows execution to continue.

Interview focus

Spill is a performance signal, not automatically a failure. A huge spill may indicate oversized partitions, skew or an operation with a large working set.

STORAGE MEMORY

Caching and persisted datasets

Storage memory holds retained dataset blocks so Spark can reuse previous computation instead of recomputing lineage.

For Spark SQL/DataFrames, in-memory caching uses a columnar representation and can automatically use compression to reduce memory and GC pressure.

Interview focus

Caching saves recomputation. It does not make a one-time computation automatically faster.

CACHE VS PERSIST

What is the difference?

cache()Convenient shorthand using a default storage level.
persist(level)Lets you explicitly choose a storage level.

Both mark a dataset for reuse. The actual caching work happens when an action computes the dataset.

Interview focus

The most important distinction is not “cache vs persist” but default storage behavior vs explicitly selected storage level.

STORAGE LEVELS

Choosing where persisted data lives

MEMORY_ONLYFastest access when it fits; uncached partitions may be recomputed.
MEMORY_AND_DISKKeep what fits in memory; store remaining persisted blocks on disk.
DISK_ONLYPersist to disk when memory is not the desired storage location.
Replicated levelsKeep copies on multiple nodes for faster recovery at higher resource cost.

Exact storage-level behavior differs by language/runtime details, so choose based on your API and Spark version.

Interview focus

Choose storage level based on recomputation cost, available memory and required access speed—not because one level is universally best.

DECISION TREE

When should you cache?

  1. Is this dataset reused by multiple downstream actions/branches?
  2. Is recomputation expensive?
  3. Does the dataset fit comfortably at the chosen storage level?
  4. Will caching reduce more work than the memory pressure it introduces?
  5. Can you unpersist it once the reuse period ends?

If the dataset is consumed only once, caching is frequently unnecessary.

Interview focus

Caching is an investment: spend memory now to avoid future recomputation.

LAZY MATERIALIZATION

When does caching actually happen?

df.cache() does not immediately load the full dataset into cache. Spark materializes cached partitions as the computation is executed by an action.

df.cache()→Still lazy→ action →Partitions computed & retained

Interview focus

A common interview trick: cache is lazy, just like transformations.

UNPERSIST

Free resources intentionally

After the dataset is no longer reused, call unpersist() so retained storage does not continue competing with future workloads.

Interview focus

Long pipelines can suffer because old cached datasets remain resident long after their usefulness has ended.

df = expensive_transform(source).cache()

df.count()       # materializes the cache
# ... reuse df ...
df.unpersist()
EVICTION

What happens when cache pressure grows?

Spark monitors cached blocks and can remove older storage blocks under pressure. Cached data is fault tolerant because lost partitions can generally be recomputed from lineage.

However, excessive eviction means you may pay both costs: memory pressure plus repeated recomputation.

Interview focus

If cached blocks keep getting evicted, investigate whether caching that dataset is worthwhile or whether the storage level/data size should change.

SPILL

Memory pressure vs spilling

Storage pressureCached blocks may be evicted or placed according to storage level.
Execution pressureIntermediate working data may spill to disk.

These are related but different behaviors. Understanding which one is occurring helps you choose the correct fix.

Interview focus

Evicted cache ≠ shuffle spill. Always identify the memory consumer.

OOM

Common OutOfMemory scenarios

One huge partitionSkew or poor partition sizing.
Huge task working setAggregation/join needs too much memory.
Over-cachingToo much retained data competes with execution.
Large broadcastReplication exceeds practical executor memory.
Object overheadMany objects consume far more than raw data.
Driver collectioncollect()/large results overwhelm driver memory.

Interview focus

The fix depends on the scenario: repartition, solve skew, reduce data, change strategy or adjust resources. One memory setting is not a universal solution.

GARBAGE COLLECTION

Why GC can slow a job

JVM garbage collection must reclaim memory from objects that are no longer needed. Object-heavy workloads with high allocation churn can spend substantial time cleaning up instead of computing.

Efficient data structures and serialized representations can reduce object overhead in appropriate JVM workloads.

Interview focus

High GC time is often a symptom of allocation and memory pressure. Treat JVM tuning as an advanced step after understanding the workload.

SERIALIZATION

Kryo and serialized storage concepts

Serialization matters when data is transferred or stored in serialized form. Efficient serialization can reduce memory footprint and network payload, though deserialization adds CPU work when data is accessed.

For JVM workloads, Spark documentation highlights Kryo as a more space-efficient option than Java serialization in many cases.

Interview focus

Smaller memory footprint and faster access are a trade-off. Serialized data can save memory but require CPU to deserialize.

PYSPARK

A PySpark-specific mental model

PySpark workloads involve both Spark's JVM execution environment and Python processes for Python-side logic. Excessive Python object processing and unnecessary UDF boundaries can therefore add serialization and process-boundary overhead.

Prefer native Spark SQL/DataFrame expressions whenever they can express the same computation.

Interview focus

Do not reduce PySpark performance to “Python is slow.” Focus on optimizer visibility, serialization and execution boundaries.

DATAFRAME CACHING

Columnar caching

Spark SQL can cache DataFrames/tables using an in-memory columnar format. This can scan only required columns from the cached representation and use compression selected for columns.

That makes DataFrame caching behavior conceptually different from thinking only in terms of storing individual row objects.

Interview focus

For SQL/DataFrame interviews, mention columnar in-memory caching and column-aware scans.

PRODUCTION CASE

Caching that makes a job slower

Scenario: A pipeline caches a 400 GB DataFrame because “cache is faster.” The DataFrame is used only once after caching.

  1. Compute the expensive dataset.
  2. Store hundreds of GB of cache blocks.
  3. Execution memory now competes with storage.
  4. Other stages experience pressure/spill or eviction.
  5. The cached dataset is never reused enough to repay its cost.

Fix: remove the unnecessary cache. Cache only the reusable expensive intermediate and unpersist it after the final reuse.

Interview focus

This is a favorite interview scenario: caching can hurt performance when it increases pressure without avoiding meaningful recomputation.

Memory optimization starts with evidence: what is stored, what is executing, and which task is actually under pressure?

🔥 Spark Memory & Caching — Interview Vault

1. What is unified memory management?

Execution and storage share a unified region, allowing memory to be used dynamically according to workload needs.

2. What is execution memory?

Working memory used by operations such as joins, sorts, aggregations and shuffle processing.

3. What is storage memory?

Memory used to retain cached and persisted datasets for reuse.

4. cache() vs persist()?

cache is a convenient default; persist lets you select an explicit storage level.

5. When should you cache?

When an expensive dataset is reused enough that avoided recomputation exceeds the memory/storage cost.

6. What happens if cached data does not fit?

Behavior depends on storage level: partitions may be recomputed, stored on disk, or managed through eviction.

7. What is spill?

Intermediate execution data exceeds available working memory and is written to disk.

8. Why can caching slow Spark?

Unnecessary cached data competes with execution memory and can create pressure, eviction and GC overhead.

9. What causes executor OOM?

Common causes include skewed partitions, huge task working sets, over-caching, large broadcasts and object overhead.

10. What is unpersist?

It marks cached data as no longer needed and removes retained blocks from memory/disk according to the API behavior.

11. Why can GC hurt performance?

Object-heavy allocation churn can cause significant time to be spent reclaiming memory instead of computing.

12. What is the memory debugging workflow?

Identify execution vs storage pressure, inspect task/partition imbalance, check spill/GC, and then apply a targeted fix.

🎯 Memory debugging formula

What is consuming memory? → Which task/partition? → Execution or storage? → Spill, eviction or OOM? → Fix the cause → Measure again.
