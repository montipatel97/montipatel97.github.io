☁️ AWS Fundamentals for Data Engineers

Core mental model

AWS data engineering is about composing managed services. Identify storage, compute, metadata, orchestration, security and observability separately before selecting products.

Regions and Availability Zones

A Region is a geographic AWS area containing multiple isolated Availability Zones. Interview answers should consider locality, resilience, compliance and data-transfer implications.

Control plane vs data plane

Configuration APIs create and manage resources; data-plane operations read, write and process the actual data. This distinction is useful when reasoning about permissions and failures.

Shared responsibility

AWS manages underlying cloud infrastructure while customers remain responsible for configuring identities, data access, encryption choices and workload security.

FOUNDATION • SECURITY

IAM Deep Dive

Authentication asks “who are you?” Authorization asks “what are you allowed to do?” For a Data Engineer, IAM is not an isolated security topic—it determines whether Glue can read S3, whether a Step Functions workflow can start a job, and whether an analyst can query cataloged data.

Principal→Policy evaluation→Allow / Deny→AWS resource

Users vs Roles

An IAM user represents a long-lived identity. A role is assumed and provides temporary credentials. For AWS services and production workloads, roles are generally the central concept you should understand.

Trust policy vs permission policy ⭐

Trust policy: who is allowed to assume the role. Permission policy: what the role can do after it has been assumed. This distinction is one of the most common AWS interview questions.

// Conceptual Glue job role
Trust:  glue.amazonaws.com → can assume this role
Permissions:
  s3:GetObject   → raw input
  s3:PutObject   → curated output
  glue:*         → required Glue operations
  logs:*         → controlled monitoring access

Least privilege

Grant only the actions, resources and conditions required. Avoid broad production permissions simply because a job “works” with them.

Data Engineer scenario

A Glue job reads s3://lake/raw/ and writes s3://lake/curated/. Its execution role needs access to those relevant locations; the developer launching the job may have a different identity and permission set.

Q: Why use an IAM role for Glue?

A: Glue assumes the role and receives permissions to access resources such as S3 on behalf of the job.

Q: Explicit deny vs allow?

A: Policy evaluation is not simply “find an allow”; an applicable explicit deny overrides an allow.

Q: How do you debug AccessDenied?

A: Identify the calling principal, requested action, target resource and all relevant identity/resource/organizational policies rather than randomly adding permissions.

FOUNDATION • DATA LAKE

Amazon S3 Deep Dive for Data Engineers

Think of S3 as the storage foundation of many AWS data lakes. Data is stored as objects inside buckets; object keys often use slash-separated names that look like folders.

Bucket→Prefix / Key→Object→Metadata

Recommended lake mental model

s3://company-lake/
  raw/
    source=crm/
      ingest_date=2026-09-08/
  silver/
    domain=customers/
      event_date=2026-09-08/
  gold/
    dataset=daily_customer_metrics/

Raw/Bronze: minimally changed source data. Silver: cleaned and standardized data. Gold: curated business-ready datasets. The exact names vary; the separation of responsibilities matters more than the labels.

Partitioning ⭐

Partition data by columns frequently used to restrict reads, often dates. A query filtering one date can avoid scanning unrelated partitions when the engine and table layout support partition pruning.

File formats

CSV and JSON are convenient for interchange, while columnar formats such as Parquet are commonly preferred for analytical workloads because queries can read relevant columns more efficiently.

Small-files problem

Millions of tiny files increase metadata and scheduling overhead. A data-engineering pipeline should consider compaction or suitable output sizing instead of only increasing compute.

S3 + Glue

Glue Spark jobs can read and write common formats in S3 and can organize output using partitions. A Glue job's IAM role must have the required bucket/object permissions.

Q: Bucket vs prefix?

A: A bucket is the S3 container; a prefix is part of an object key used to organize and group objects.

Q: How do you design an S3 data lake?

A: Separate lifecycle stages, use predictable prefixes, choose query-aware partitions, prefer analytics-friendly formats where appropriate and manage file sizes.

Q: Why not partition by a very high-cardinality column?

A: It can create excessive tiny partitions/files and metadata overhead with little pruning benefit.

Q: How would you secure S3 pipeline data?

A: Use least-privilege IAM, control bucket access, use appropriate encryption and audit access according to the workload's requirements.

🎯 Foundation Interview Drill

Design question: File lands in S3. What happens next?

Describe event/trigger detection, metadata discovery if needed, transformation compute, curated output, catalog updates, monitoring and failure handling.

Glue cannot read S3. Where do you look?

Start with the Glue execution role and the required bucket/object permissions, then check encryption and any relevant resource-level restrictions.

How do you reduce query cost on a data lake?

Read less data: partition pruning, selecting fewer columns, columnar storage and sensible file layout are usually stronger starting points than blindly adding compute.
