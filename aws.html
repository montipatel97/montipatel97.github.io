☁️ AWS Fundamentals for Data Engineers

Core mental model

AWS data engineering is about composing managed services. Identify storage, compute, metadata, orchestration, security and observability separately before selecting products.

Regions and Availability Zones

A Region is a geographic AWS area containing multiple isolated Availability Zones. Interview answers should consider locality, resilience, compliance and data-transfer implications.

Control plane vs data plane

Configuration APIs create and manage resources; data-plane operations read, write and process the actual data. This distinction is useful when reasoning about permissions and failures.

Shared responsibility

AWS manages underlying cloud infrastructure while customers remain responsible for configuring identities, data access, encryption choices and workload security.

FOUNDATION • SECURITY

IAM Deep Dive

Authentication asks “who are you?” Authorization asks “what are you allowed to do?” For a Data Engineer, IAM is not an isolated security topic—it determines whether Glue can read S3, whether a Step Functions workflow can start a job, and whether an analyst can query cataloged data.

Principal→Policy evaluation→Allow / Deny→AWS resource

Users vs Roles

An IAM user represents a long-lived identity. A role is assumed and provides temporary credentials. For AWS services and production workloads, roles are generally the central concept you should understand.

Trust policy vs permission policy ⭐

Trust policy: who is allowed to assume the role. Permission policy: what the role can do after it has been assumed. This distinction is one of the most common AWS interview questions.

// Conceptual Glue job role
Trust:  glue.amazonaws.com → can assume this role
Permissions:
  s3:GetObject   → raw input
  s3:PutObject   → curated output
  glue:*         → required Glue operations
  logs:*         → controlled monitoring access

Least privilege

Grant only the actions, resources and conditions required. Avoid broad production permissions simply because a job “works” with them.

Data Engineer scenario

A Glue job reads s3://lake/raw/ and writes s3://lake/curated/. Its execution role needs access to those relevant locations; the developer launching the job may have a different identity and permission set.

Q: Why use an IAM role for Glue?

A: Glue assumes the role and receives permissions to access resources such as S3 on behalf of the job.

Q: Explicit deny vs allow?

A: Policy evaluation is not simply “find an allow”; an applicable explicit deny overrides an allow.

Q: How do you debug AccessDenied?

A: Identify the calling principal, requested action, target resource and all relevant identity/resource/organizational policies rather than randomly adding permissions.

FOUNDATION • DATA LAKE

Amazon S3 Deep Dive for Data Engineers

Think of S3 as the storage foundation of many AWS data lakes. Data is stored as objects inside buckets; object keys often use slash-separated names that look like folders.

Bucket→Prefix / Key→Object→Metadata

Recommended lake mental model

s3://company-lake/
  raw/
    source=crm/
      ingest_date=2026-09-08/
  silver/
    domain=customers/
      event_date=2026-09-08/
  gold/
    dataset=daily_customer_metrics/

Raw/Bronze: minimally changed source data. Silver: cleaned and standardized data. Gold: curated business-ready datasets. The exact names vary; the separation of responsibilities matters more than the labels.

Partitioning ⭐

Partition data by columns frequently used to restrict reads, often dates. A query filtering one date can avoid scanning unrelated partitions when the engine and table layout support partition pruning.

File formats

CSV and JSON are convenient for interchange, while columnar formats such as Parquet are commonly preferred for analytical workloads because queries can read relevant columns more efficiently.

Small-files problem

Millions of tiny files increase metadata and scheduling overhead. A data-engineering pipeline should consider compaction or suitable output sizing instead of only increasing compute.

S3 + Glue

Glue Spark jobs can read and write common formats in S3 and can organize output using partitions. A Glue job's IAM role must have the required bucket/object permissions.

Q: Bucket vs prefix?

A: A bucket is the S3 container; a prefix is part of an object key used to organize and group objects.

Q: How do you design an S3 data lake?

A: Separate lifecycle stages, use predictable prefixes, choose query-aware partitions, prefer analytics-friendly formats where appropriate and manage file sizes.

Q: Why not partition by a very high-cardinality column?

A: It can create excessive tiny partitions/files and metadata overhead with little pruning benefit.

Q: How would you secure S3 pipeline data?

A: Use least-privilege IAM, control bucket access, use appropriate encryption and audit access according to the workload's requirements.

🎯 Foundation Interview Drill

Design question: File lands in S3. What happens next?

Describe event/trigger detection, metadata discovery if needed, transformation compute, curated output, catalog updates, monitoring and failure handling.

Glue cannot read S3. Where do you look?

Start with the Glue execution role and the required bucket/object permissions, then check encryption and any relevant resource-level restrictions.

How do you reduce query cost on a data lake?

Read less data: partition pruning, selecting fewer columns, columnar storage and sensible file layout are usually stronger starting points than blindly adding compute.

GLUE • ETL + CATALOG

AWS Glue Masterclass

Glue architecture

Glue provides serverless data integration. Core interview components are jobs, Data Catalog, crawlers, connections, triggers/workflows and monitoring.

Data Catalog

A centralized metadata repository containing database, table, schema and related metadata used across analytics services.

Crawlers

Crawlers scan supported data sources and infer/catalog metadata. Use them when automated discovery is appropriate; do not assume they are required for every controlled production table.

DynamicFrame vs DataFrame

DynamicFrames are Glue-oriented abstractions useful for semi-structured or evolving data. DataFrames give the familiar Spark API and ecosystem. Choose based on transformation needs rather than habit.

GlueContext

The Glue-aware context exposes Glue integrations and DynamicFrame operations around the Spark environment.

Job bookmarks

Use bookmarks to help avoid reprocessing eligible previously processed input in supported patterns; understand the source and key semantics before relying on them as a universal incremental solution.

Connections

Connections store configuration needed to reach supported data stores; network and IAM design still matter.

Triggers and workflows

Glue can chain jobs/crawlers through triggers and workflows; Step Functions is often chosen when richer branching, retries and cross-service orchestration are required.

Monitoring

Use Glue run information, logs, job insights and Spark UI where available. Debug with evidence from stage/task behavior and data volume.

Glue PySpark pattern

from awsglue.context import GlueContext
from pyspark.context import SparkContext
from awsglue.job import Job

sc = SparkContext.getOrCreate()
glueContext = GlueContext(sc)
spark = glueContext.spark_session

source = glueContext.create_dynamic_frame.from_catalog(
    database="lake", table_name="raw_events"
)
df = source.toDF().filter("event_id is not null")
(df.write.mode("append").parquet("s3://lake/silver/events/"))

ATHENA • SERVERLESS SQL

Amazon Athena Deep Dive

Mental model

Athena runs SQL against data sources such as S3 using metadata from a catalog; data layout is therefore part of query performance.

Catalog relationship

Athena commonly uses the AWS Glue Data Catalog for databases and table metadata.

Cost/performance mindset

Reduce data scanned: partition pruning, selecting required columns, columnar formats and good file layout are foundational.

Partitions

Partition by useful filters such as date when it matches query patterns. Excessive partitions can create operational overhead.

CTAS and transformations

Use SQL-based patterns to create optimized derived datasets where appropriate.

Workgroups

Use workgroup controls to separate workloads and apply governance/cost-management settings.

Interview scenario

A query is expensive: inspect bytes scanned and file/partition layout before assuming SQL compute itself is the bottleneck.

REDSHIFT • WAREHOUSE

Amazon Redshift Deep Dive

Mental model

A managed analytical data warehouse for structured, large-scale analytical workloads.

Distribution design

Distribution choices affect where rows live and how much data must move for joins. The right choice depends on table size and join patterns.

Sort design

Sort design can improve scans when predicates align with the physical ordering characteristics.

COPY and UNLOAD

Common data-engineering patterns load data into Redshift and export results through supported high-throughput mechanisms rather than row-by-row inserts.

Spectrum concept

External data access can extend analytics to data stored outside the warehouse, including S3-backed datasets.

Interview scenario

Choose distribution and sort strategy from workload evidence—table sizes, joins and filters—not from a universal template.

EMR • BIG DATA

Amazon EMR Deep Dive

When EMR

Choose EMR when you need managed big-data frameworks and more flexibility/control over runtime and distributed processing.

Spark connection

Your existing Spark knowledge transfers directly: executors, partitions, shuffle, skew and configuration still determine application behavior.

Glue vs EMR

Glue emphasizes serverless data integration; EMR is generally the better fit when you need broader framework/runtime control. Explain workload requirements rather than claiming one is always better.

Catalog integration

EMR Spark can use the AWS Glue Data Catalog as shared metadata, supporting a common lake/catalog architecture.

Interview scenario

A highly customized Spark workload with specialized libraries and runtime tuning requirements may favor an EMR deployment model over a simplified serverless ETL abstraction.

ORCHESTRATION

Lambda, Step Functions & Event-Driven Pipelines

Lambda

Event-driven serverless compute for lightweight processing, validation, API calls and orchestration helpers.

Step Functions

State machines make retries, branching, parallel steps and workflow state explicit. They can coordinate services including Glue and other AWS services.

Standard vs Express

Understand the trade-off between long-running/auditable workflow needs and high-volume event processing characteristics.

EventBridge

Useful for reacting to AWS events and routing them to targets such as Lambda, Step Functions, SNS or SQS.

Pipeline pattern

S3/Event → validation → orchestration → Glue/EMR processing → catalog/query → notification/monitoring.

Failure design

Use explicit retries where safe, idempotent processing where possible, dead-letter/error paths where appropriate, and alerting for human action.

MESSAGING + NOSQL

SNS, SQS & DynamoDB

SQS

A queue used to decouple producers and consumers. Consumers process messages independently, helping absorb bursts.

SNS

Publish/subscribe fan-out: one publisher can notify multiple subscribers.

SNS + SQS

A common fan-out pattern publishes once and delivers copies to multiple queues/subscribers for independent downstream processing.

DLQ

A failure destination for messages that repeatedly cannot be processed according to configured handling. Investigate root cause rather than endlessly replaying bad data.

DynamoDB

Design starts from access patterns and keys. For Data Engineers, DynamoDB Streams can also participate in change/event-driven architectures.

Idempotency

Distributed delivery can produce retries or duplicates; design consumers and writes so repeating a logically identical event does not corrupt results.

OBSERVABILITY

CloudWatch & Production Operations

Logs

Capture actionable application and pipeline diagnostics; include identifiers that allow a failed input/run to be traced.

Metrics

Monitor latency, throughput, failures, backlog, data volume and quality signals.

Alarms

Alert on symptoms requiring action, not every harmless log line.

Runbook mindset

For every important alarm, document what it means, likely causes, first checks and recovery steps.

Debugging flow

Symptom → CloudWatch/job evidence → isolate stage/service → validate permissions/data/runtime → targeted fix → confirm recovery.

Data quality

Operational success is not enough. A job that finishes successfully can still publish incorrect or incomplete data.

SYSTEM DESIGN

End-to-End AWS Data Engineering Architecture

Batch lakehouse pattern

Sources → S3 landing → EventBridge/Step Functions → Glue/EMR → curated S3 → Glue Catalog → Athena/Redshift → consumers.

Streaming pattern

Events → streaming ingestion → stream processing → durable storage → curated/query layer → monitoring and alerts.

Failure strategy

Separate transient infrastructure failures from deterministic bad data; use retries carefully and route unrecoverable records to an observable quarantine path.

Security strategy

Service roles, least privilege, encryption requirements and clear separation of data access responsibilities.

Interview answer structure

Requirements → data flow → service selection → security → scaling → failure handling → monitoring → trade-offs.

Always explain what problem the service solves, where it sits in the architecture, how it fails, and the trade-off against nearby AWS services.
