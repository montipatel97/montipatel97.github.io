🚀 Query Optimization

Diagnose slow queries using evidence from plans, data distribution and measured bottlenecks.

EXPLAIN & plans

EXPLAIN shows the optimizer strategy; some engines provide actual execution statistics.

Interview focus

Read scan type, joins, row estimates versus actuals, sorts and expensive nodes.

Filter early

Reduce rows as early as semantics allow and avoid fetching unnecessary columns.

Interview focus

SELECT * and late filters can increase I/O and network cost.

Sargability

Write predicates so indexes can be used effectively.

Interview focus

Avoid unnecessary functions or casts on indexed columns when a range predicate works.

Join optimization

Join order, cardinality, indexes and algorithm choice can dominate performance.

Interview focus

Know nested-loop, hash and merge joins conceptually.

Statistics

Optimizers rely on statistics to estimate row counts and costs.

Interview focus

Bad estimates can lead to poor join order or algorithm choice.

N+1

Many repeated small queries can be slower than a suitable set-based query.

Interview focus

Identify N+1 patterns in application/database interactions.

Partitioning

Large tables may be partitioned so pruning reduces data scanned.

Interview focus

Partitioning is not indexing; explain pruning and maintenance trade-offs.

Workflow

Measure → inspect plan → identify bottleneck → change → measure again.

Interview focus

Never add indexes blindly; validate representative workloads.

Quick interview recap

  1. EXPLAIN & plans: Read scan type, joins, row estimates versus actuals, sorts and expensive nodes.
  2. Filter early: SELECT * and late filters can increase I/O and network cost.
  3. Sargability: Avoid unnecessary functions or casts on indexed columns when a range predicate works.
  4. Join optimization: Know nested-loop, hash and merge joins conceptually.
  5. Statistics: Bad estimates can lead to poor join order or algorithm choice.
